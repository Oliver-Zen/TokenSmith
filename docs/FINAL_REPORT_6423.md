# Final Project Report

**Repository:** [TokenSmith](https://github.com/Oliver-Zen/TokenSmith/tree/oliver/cs6423-spr26-project)

## Project Summary

My project studies how database-style query optimization ideas can improve a local Retrieval-Augmented Generation system. The base system is TokenSmith, an on-device RAG pipeline that indexes the Silberschatz database textbook, retrieves relevant chunks with FAISS and BM25, optionally reranks them, and generates answers with local GGUF models through `llama.cpp`. The motivating problem is that TokenSmith originally used one static pipeline for every question, even though simple definitional questions and harder analytical questions clearly do not need the same retrieval budget or ranking strategy. I framed this as a database systems problem: if a DBMS uses a query optimizer to choose different physical plans for different SQL queries, then a RAG system should also be able to choose a plan per query instead of always running the same fixed configuration.

The proposal organized the project into three tiers. The 75% goal was to integrate a rule-based query planner into the real TokenSmith execution path. The 100% goal was to move beyond rule-based planning and implement cost-based plan enumeration and budget-aware selection. The 125% goal was to add feedback-driven adaptation through online updates, plan caching, and Pareto-style quality/latency analysis. The final state of the project is that the 75% milestone is fully completed, the main engineering pieces of the 100% milestone are implemented, and a substantial portion of the 125% stretch work is implemented as well. The strongest result is that the optimizer is no longer only a proposal artifact; it is now a real component used by the chat path, the API path, and the benchmark/reporting path.

## Proposed Goals and Progress

For the 75% milestone, I proposed integrating the planner into the actual RAG pipeline, strengthening the query classifier, and mapping query classes to different `RAGConfig` settings. This portion is complete. TokenSmith now has a functioning `HeuristicQueryPlanner` that classifies queries into definitional, explanatory, analytical, and procedural categories based on question word, query length, comparison language, procedural cues, and entity density. The planner is not dead code: it is invoked on every query when planner mode is enabled, and its effective per-query configuration is consumed by retrieval, ranking, and generation. I also refactored runtime setup so that indexes stay loaded once while lightweight query-specific retrievers and rankers are rebuilt per query. That change was necessary to make planning actually work end to end.

For the 100% milestone, I proposed defining a plan space, building a cost model, and selecting a plan from the Pareto frontier under a latency budget. I made substantial progress here. TokenSmith now supports `cost_based` planner mode in addition to `heuristic`. The new planner enumerates valid plans over retrieval weights, ensemble method, candidate pool size, top-k adjustments, HyDE on/off, reranking on/off, and double prompting on/off. For each candidate plan it estimates latency and expected quality, computes a Pareto frontier, and chooses the best frontier plan that satisfies the configured latency budget when possible. I also added richer planner metadata so the selected plan ID, estimated latency, estimated quality, and candidate frontier are logged and available to the API and reporting code. What is still incomplete is the fully data-driven part of the original 100% goal: the current cost model is hand-crafted and calibrated from system intuition rather than learned from a large historical benchmark table or regression fit over collected runtime statistics. In other words, the optimizer exists and makes real decisions, but its model is still engineered rather than learned.

For the 125% milestone, I proposed feedback-driven adaptation, plan caching, and multi-objective analysis. Here again, a meaningful subset is implemented. TokenSmith now supports an `adaptive` planner mode that extends the cost-based planner with online feedback updates using exponential moving averages, a cache from query-class signatures to successful plans, and planner snapshots that expose feedback and cache state. The benchmark/reporting layer was extended so results can include selected plans, cache hits, estimated latency and quality, and Pareto frontier metadata. The HTML report generator also now has explicit plan-analysis and Pareto-visualization support. The part that remains incomplete is the strongest version of the original stretch goal: the runtime currently uses lightweight proxy signals and benchmark-provided scores where available rather than a robust online answer-quality estimator such as a well-calibrated LLM judge or a large human-labeled dataset. So the adaptive loop is present, but the quality signal still needs stronger empirical grounding.

## Correctness Testing

I tested correctness at three levels: unit testing of planner logic, integration testing of the API/runtime path, and manual inspection of planner-aware query logs. The first layer was planner-specific unit coverage. I added tests that verify query classification for representative questions, category-to-configuration mapping, metadata propagation through `resolve_query_config()`, cost-based planner construction, Pareto-plan selection under a budget, adaptive feedback updates, and plan-cache reuse for later related queries. These tests matter because the planning layer changes runtime configuration dynamically; without this coverage, it would be easy to break query-specific execution silently.

The second layer was API and execution-path testing. I ran the project environment’s pytest suite for the planner and API surfaces, specifically `tests/test_planner.py`, `tests/test_api_server.py`, and `tests/test_api.py`. The combined result was **78 passing tests**. These tests verify that the planner can be built in the new modes, that planner metadata reaches the API responses, that retrieval/ranking helpers still behave correctly, and that the chat and streaming endpoints continue to function after the optimizer changes. During implementation I also had to fix compatibility regressions in `src/api_server.py` so older helper behavior used by the tests continued to work while still supporting the new planner path.

The third layer was manual validation through real chat logs. This was important because many failure modes in local RAG are not pure logic bugs; they are systems bugs involving context windows, retrieval/reranking interactions, or plan-specific runtime assumptions. I inspected planner-aware logs to confirm that the selected configuration actually matched the predicted query type and that the retrieved textbook chunks were reasonable. I also verified that adaptive planner metadata such as selected plan ID, budget, estimated latency, and Pareto frontier were being persisted into the log files. This manual inspection is not a substitute for larger benchmarking, but it is valuable because it confirms that the optimizer is active in the true runtime, not only in isolated tests.

## Experimental Results Collected to Date

The empirical story of the project is strongest on planner behavior and observability, and weaker on large-scale final benchmark tables. I collected three kinds of experimental evidence. First, the heuristic planner demonstrably changes the execution plan in ways consistent with the proposal. For the logged query “What does it mean for two database schedules to be conflict equivalent?”, TokenSmith classified the query as **definitional** and changed the plan from the default FAISS-heavy RRF configuration to a **linear BM25-heavy configuration with no reranking** and a smaller candidate pool (`num_candidates` dropped from 50 to 40). That is exactly the kind of cheap, lexical, definition-oriented plan the project aimed to produce for short factual questions.

Second, for a more process-oriented question, “How does strict two-phase locking help with recoverability?”, the heuristic planner classified the query as **procedural** and selected a wider, more expensive retrieval setup: the candidate pool increased to 60, the ranking weights became more balanced across FAISS and BM25 with index-keyword support, and reranking depth increased from 5 to 8. This shows that the planner is not merely categorizing queries for logging; it is actually pushing the retrieval pipeline toward broader evidence collection on questions that are more likely to require multi-step explanations. That is an important systems result because it validates the core premise of adaptive execution.

Third, the adaptive planner now produces explicit cost-based optimization traces. In the logged adaptive query “what is concurrency control,” the planner enumerated **15 candidate plans**, built a Pareto frontier, and selected the plan `defi_lexical_c5_k+0_plain_base_single` under a configured **900 ms latency budget**. The planner’s own metadata reported an estimated latency of **450.5 ms** and an estimated quality of **0.85**, with three frontier candidates visible in the log. This is the clearest evidence that the project reached beyond rule-based query classes into actual budget-aware plan selection. The same log also shows the cache key and feedback counters that support the later adaptive step.

The answer-quality side of the experimental story is mixed, which is important to state honestly. Some logged outputs are encouraging: the conflict-equivalence query returned the textbook notion that conflict equivalence can be obtained by swapping non-conflicting instructions, which is close to the desired definition. Other answers are clearly less satisfactory. The strict two-phase locking answer retrieved very relevant textbook chunks, but the generated answer still overgeneralized and mixed together serializability, deadlock, and rollback discussion instead of cleanly focusing on recoverability and cascading rollback prevention. In other words, adaptive retrieval and ranking improved observability and plan control, but generation quality is still uneven on subtle concurrency-control questions. That is a real experimental result, not just a caveat, and it points directly to the remaining work on evaluation and calibration.

I also extended the benchmark/reporting infrastructure so that future experiments can be run more systematically. Results can now record planner mode, query category, selected plan ID, cache usage, estimated latency/quality, and Pareto frontier metadata. The reporting layer can also summarize plan usage and render Pareto-style quality/latency plots. However, the full final four-way benchmark comparison from the proposal remains incomplete. The main blocker is evaluation practicality: some legacy benchmark metrics depend on heavyweight or external models, and full local benchmark runs are brittle because the embedding stack is sensitive to execution context. As a result, the project’s final empirical contribution is best described as **strong optimizer integration with preliminary planner results**, rather than a fully completed benchmark paper with exhaustive quantitative tables.

## Future Work

The next concrete task is to make the cost model genuinely data-driven. Right now the optimizer’s quality and latency estimates are engineered heuristics. The natural next step is to run a larger benchmark workload, collect per-plan latency and quality outcomes, and fit the model from those observations rather than from hand-tuned coefficients. That would complete the strongest version of the 100% goal.

The second task is to expand and stabilize evaluation. The current benchmark suite has only 11 textbook questions, which is enough to test plumbing but not enough to support strong claims about generalization across query categories. I would like to extend the suite to at least 25 to 40 questions, rebalance it across definitional, explanatory, analytical, and procedural cases, and ensure that all metrics can run in a fully local and reproducible way. In particular, I would like to remove accidental dependence on external judges for routine evaluation and replace it with a dependable local scoring pipeline plus occasional manual review.

The third task is to improve the adaptive signal. The present adaptive planner can update EMAs and cache successful plans, but the quality signal is still relatively weak. A better version would combine benchmark-based supervision, retrieval diagnostics, and a calibrated local or offline judge so that the online updates reflect actual answer quality rather than only proxy information. Persisting this adaptive state across sessions would also make the system behave more like a real query optimizer rather than a per-process experiment.

The fourth task is to improve answer quality on difficult database concepts. The retrieval side is now much more configurable, but the generator still sometimes produces vague or blended explanations even when the right chunks are retrieved. Better prompt design, improved context packing, targeted reranking for concurrency-control topics, and stronger local generation models would likely produce larger user-visible gains than further optimizer tuning alone.

## Conclusion

The main outcome of this project is that TokenSmith now supports real query planning rather than a single static RAG pipeline. The heuristic planner is fully integrated, the cost-based planner can enumerate and choose plans under a latency budget, and the adaptive planner can update preferences and cache successful query-class decisions. I also added the testing and reporting scaffolding needed to make the planner observable and debuggable. The final system therefore makes good progress on both the 100% goal and part of the 125% goal.

At the same time, the project is not finished in the scientific sense. The optimizer exists, but the cost model is not yet learned from a large benchmark corpus, and the final empirical comparison across all baselines is still preliminary. That is the clearest summary of progress to date: the systems architecture for adaptive local RAG optimization is now in place and working, and the remaining work is to turn that architecture into a stronger empirical evaluation with better calibration, better benchmarks, and better answer-quality signals.
